How embedding works

Who talks to whom on every embedded page: your page, the SDK, an iframe, the cluster and your backend.

The browser holds a UI iframe and a short-lived token. Anything privileged happens on your backend.

Which embed component?

Multi-tenant SaaS: default to LiveboardEmbed and SearchEmbed with a tightly chosen action set. Avoid AppEmbed unless every customer should see ThoughtSpot navigation. Your backend decides which tenant a token belongs to.

You can embed a plain iframe if your host disallows custom JavaScript. How ThoughtSpot connects to your login

Your users already sign in with your own IdP (Okta, Auth0, Cognito, Entra) or a custom login. There are two ways to connect that login to ThoughtSpot.

Way A · AuthType.EmbeddedSSO

ThoughtSpot signs the user in

ThoughtSpot redirects the user to your SAML or OIDC IdP inside the iframe, reusing the SAML/OIDC setup already on ThoughtSpot. docs GA

  • Who does what: ThoughtSpot talks to the IdP. Your backend does nothing.
  • Fits when: one SAML or OIDC IdP that allows iframe redirects, and SSO already configured on ThoughtSpot. docs
or
Way B · TrustedAuthTokenCookieless

Your app signs the user in, then vouches

Your app logs the user in its own way. Your backend then asks ThoughtSpot for a token for that user, using a secret key. docs GA

Trusted auth, step by step

Phase A is the login your app already has. Phase B is the new part: your backend vouches for that user to ThoughtSpot.

The session cookie proves the user to your backend. The secret key proves your backend to ThoughtSpot. Two credentials, two trust relationships.

What goes in the token request

One auth/token/custom call answers three questions about the user. Only username and persist_option are required. docs

⚿Who is this?username, secret_key, org_identifier, validity_time_in_sec (default 300)
＋Create them on first visit?JIT: auto_create, display_name, email, groups
⛨Which rows may they see?ABAC: variable_values + persist_option, optionally scoped with objects

Just-in-time users: the conditions

  • Send auto_create: true with display_name, email and groups ([{ "identifier": "…" }]) for users who may not exist yet. docs
  • Use the secret_key: JIT provisioning requires it. docs
  • Check privileges: adding a user during auto-creation requires ADMINISTRATION, or under RBAC CONTROL_TRUSTED_AUTH plus edit access to the data source. docs
  • Expect JIT to update an existing user: with auto_create: true their display name, email, Org and group entitlements are not changed. docs
  • Expect it to create formula variables. It creates the user (and any new groups, with default options), never the variables. docs
  • Forget the default: auto_create is true on auth/token/custom (10.5.0.cl+) but false on auth/token/full. docs

ABAC with RLS: how the values reach a query

1Create the variableA formula variable, once, via template/variables/create
→
2Reference it in RLSThe table's RLS rule reads the variable
→
3Send values in the tokenvariable_values per user, at mint time
→
4Every query is filteredModels, Liveboards, Answers and Spotter
Watch for these

The variable must already exist: name refers to an existing formula variable. docs

With variable_values, persist_option must be APPEND or REPLACE. RESET and NONE work only without them. docs

Values are written to the user's profile when the token is created, not when it is used, and later sessions keep using them. A token you mint and throw away still changes the user. docs

Version gates differ between pages (the REST field says 10.14.0.cl, the ABAC guide says 10.15.0.cl), and RLS, not runtime filters, is the security boundary. Details in Data security.

The token endpoint does six jobs

The path is yours (/ts-token or anything else). ThoughtSpot does not provide this endpoint, and every security property of the integration passes through it.

→
3ResolveLook up groups or RLS values server-side.

Go deeper: the endpoint in code about 3 min
import express from 'express';

const app = express();
const TS_HOST = process.env.TS_HOST;            // https://your-instance.thoughtspot.cloud
const SECRET_KEY = process.env.TS_SECRET_KEY;   // from your secrets manager, never sent to the browser

// 1. requireAppSession rejects unauthenticated requests (401).
app.get('/ts-token', requireAppSession, async (req, res) => {
  // 2. Identity comes from YOUR verified session, not from req.query or req.body.
  const username = req.user.email;

  const tenant = await lookupTenant(req.user);   // your data: org, groups, RLS values

  const r = await fetch(`${TS_HOST}/api/rest/2.0/auth/token/custom`, {
    method: 'POST',
    headers: {
      'Accept': 'application/json',
      'Content-Type': 'application/json',
      'X-Requested-By': 'ThoughtSpot',
    },
    body: JSON.stringify({
      username,
      secret_key: SECRET_KEY,
      validity_time_in_sec: 300,           // bearer credential: keep short, autoLogin refreshes it
      org_identifier: tenant.org,          // only if Orgs are enabled
      persist_option: 'REPLACE',           // required; APPEND or REPLACE when sending variable_values
      // JIT: create the user on first visit (existing users are not updated)
      auto_create: true,
      display_name: req.user.name,
      email: req.user.email,
      groups: [{ identifier: tenant.group }],
      // ABAC: values for the formula variable your RLS rule reads
      variable_values: [{ name: 'allowed_regions', values: tenant.regions }],
    }),
  });

  if (!r.ok) {
    console.error('token mint failed', r.status); // 6. audit log, no secrets
    return res.status(502).json({ error: 'token_unavailable' });
  }
  const { token } = await r.json();
  res.set('Cache-Control', 'no-store');
  res.json({ token });
});

The fields follow the auth/token/custom reference. docs allowed_regions and lookupTenant are placeholders for your own names.

Go deeper: four bugs to look for in review about 2 min

These are review guidance from experience. The linked docs cover the underlying facts.

1. Identity from the request body

The browser sends { tenant, region } and the backend stamps it in. A user edits the body and gets someone else's scope.

Fix: read identity from your verified session, then look up entitlements server-side. docs

2. Secret key in git or the browser

The key allows a token request for any username with no further authentication. A leaked key lets anyone sign in as anyone.

Fix: keep it in a secrets manager, never in the browser. docs

3. Endpoint without auth middleware

The route is reachable with no session, so anyone can mint tokens. Easy to miss behind a load balancer.

Fix: require your app session on the route, and test that an unauthenticated call returns 401.

4. Token lifetime is a security setting

A cookieless token is a bearer credential: whoever holds it acts as that user until it expires, and activity never extends it. docs A long lifetime widens the window for a leaked token and for offboarding.

Fix: keep it as short as your refresh handles. autoLogin: true fetches a new token before expiry, so users are not signed out. docs Revoke at sign-out and offboarding. docs

Plan for rotation

Disabling trusted authentication invalidates the previous secret key, and a new key is generated when it is enabled again. docs Rehearse the cutover (new key into your secrets manager, confirm the service reads it) so rotation is a runbook step, not an outage. That runbook is our guidance, not a docs procedure.

Go deeper: the four questions teams always ask about 3 min
If we use trusted auth, what is the point of OIDC? Are they substitutes?

No. They sit at different layers. Your IdP (OIDC or SAML) signs the human into your app. Trusted auth lets your backend get a token from ThoughtSpot for the user your app already knows. The docs' implementation steps for trusted auth are: enable it, build the token service, and add the SDK. Configuring SAML or OIDC on ThoughtSpot is not one of them. docs

What is in the session cookie, and does ThoughtSpot see it?

It is your app's own cookie, and it never reaches ThoughtSpot. Your token service reads the logged-in user from your session, a JWT or LDAP/AD. docs ThoughtSpot only checks the secret key. If the endpoint skips the session check, anyone who knows a username could request that user's token.

How are users created in ThoughtSpot? Is there a separate provisioning call?

Not necessarily. With auto_create: true the token request creates the user if missing. You must send display_name and email; send group_identifiers only if you want JIT group assignment. The docs warn that this creates users and any new groups with default options, and that the users and groups endpoints give full control. docs The token service may also call other REST APIs, using a service account with administrator privileges. docs

We have two IdPs, Okta for customers and Entra for staff. How does that work?

Both sign users into your app, and both end at the same backend. The docs recommend trusted authentication for multiple IdPs without federation, because ThoughtSpot sees one kind of token request from one trusted service. docs Routing by subdomain or email domain is your app's job.

Go deeper: cookie rules about 1 min
  • Use cookieless trusted auth. It has no dependency on cookies.
  • Or put ThoughtSpot on a custom domain under the same top-level domain as your app, so the cookie is first-party.
  • If you must use cookie-based or None in non-Safari browsers, enable partitioned cookies in Develop > Security Settings or via cluster_preferences.enable_partitioned_cookies. docs
  • Do not rely on partitioned cookies to fix Safari. The docs state Safari blocks all third-party cookies and does not support partitioned cookies.
  • Do not detect cookie access with detectCookieAccessSlow unless needed. The docs call it slower and say it should be avoided. docs

If cookies are blocked in cookie-based mode, the SDK emits EmbedEvent.NoCookieAccess and you should switch to cookieless. Because the token is used once, the docs suggest a validity under a minute. docs

Token lifetime and refresh

1MintDefault validity is 300 seconds. Activity never extends a v2 token.
→
2RefreshautoLogin: true requests a new token before expiry.
→
3RevokeOn sign-out, call POST /api/rest/2.0/auth/token/revoke.

A cookieless token is a bearer credential until it expires. Keep it short and let autoLogin refresh it. docs

Lifetime is a trade-off, and security wins ties

The default is 300 seconds. For cookieless the docs say you may want "20 or 30 minutes, or more", and for cookie-based under a minute, because the token is used once to open a session. docs The longer cookieless suggestion saves token requests. It is not a security recommendation.

A longer token means a stolen token works longer and a removed user keeps access until it expires (or until you revoke it). docs Our guidance: start at the default, lengthen only if refreshes cause visible problems, keep the token in memory rather than in storage or URLs, and size your token service for the extra requests.

One documented exception: for Spotter, set the token to at least 10 minutes, because Spotter workflows can run longer, and keep refreshAuthTokenOnNearExpiry on. docs

Go deeper: refresh options, v1 tokens and endpoints about 3 min
  • autoLogin: true makes the SDK request a new token before the current one or the session expires, so the user never sees a signed-out embed. docs
  • refreshAuthTokenOnNearExpiry is a view config option (documented on AppViewConfig, SearchViewConfig and the conversation view configs) and defaults to true. New SDK 1.45.2+ · TS 26.3.0.cl+ docs
  • Revoke on sign-out especially if you issue long-lived cookieless tokens. docs
V1 tokens behave differently

Legacy v1 tokens (cookie-based only) stay valid until another is generated, generating a new secret key invalidates all earlier tokens, and repeated login attempts with an expired token can lock the user out. Cookieless does not support v1 tokens. docs

Go deeper: why per-user, and the license question about 2 min

The docs note that many ThoughtSpot features are tied to individual user accounts with a valid email address, and that JIT provisioning and the user REST APIs make creating them easy. Shared customer-level or role-level accounts are possible, but the docs say to discuss them with your ThoughtSpot team because of access-control and RLS implications. The per-user recommendation below is our reasoning from that. docs

Audit

With one shared user, every action in ThoughtSpot logs as that user. You cannot answer "who changed or exported this". This is our reasoning; the docs do not discuss audit logging here.

Row-level security

RLS and ABAC rules attach to the user. A shared user can have only one set of rules, and per-person rules persisted on it can overwrite each other between concurrent sessions (our inference: persisted values are stored on the user object). docs

Personalization and content

Favorites, saved Answers, private content and sharing are per user. A shared account makes them shared too.

Scheduled and async work

Schedules and alerts run as a user. Persisted values for a user are used for scheduled reports, so they are only meaningful if the user maps to one person. docs

Three-question test

Should different people see different data? Does any work run when they are not looking (schedules, alerts)? Will anyone ever ask "who did that"? If you answer yes to any, use per-user accounts. A shared account is defensible only for public, read-only, identical views. The docs describe a dedicated public user with a tight ACL for that case. docs

"But per-user accounts cost more licenses"

Cost is a commercial question, not a technical one. The embedded license types differ: an "Embed Add-on" for internal apps used by your employees, and "ThoughtSpot Embedded" for customer-facing or public apps. docs If per-user pricing is the blocker, raise it in the contract. Go deeper: which pattern when about 2 min

ABAC variables are one of three ways to carry per-user entitlements into RLS. The right one depends on how often entitlements change and whether you have a place to mint tokens. The RLS rules page lists direct and ACL-table patterns and points to ABAC variables for dynamic attributes. docs

The rule uses the system variable ts_groups (or ts_username). Example: tenant IN ts_groups, or region = ts_username. ThoughtSpot compares against group name, which must match your database values exactly, and group names and usernames cannot be changed after creation. docs

  • Good for stable, coarse attributes: tenant, tier, department.
  • Limit: one group per value leads to group explosion. Keep RLS groups separate from role and content groups.

Formula variables set from variable_values in the token request, as above. Your backend decides the values on every login.

  • Good for dynamic or multi-valued attributes, and many dimensions at once (region AND product).

  • Limit: join cost on every query, a pipeline to maintain, and usernames must match exactly.

function utcEpoch(ymd) {
  const [y, m, d] = ymd.split('-').map(Number);
  return Date.UTC(y, m - 1, d) / 1000;        // not new Date(ymd).getTime()

If you keep filter state as strings (in a form or a URL), convert at the moment you trigger, not when you store.

Because the event appends per column, "send what changed" leaks stale columns. A column the user removed in your UI stays applied in ThoughtSpot until you clear it. Keep one source of truth in your app, and on every change push the whole desired set plus clears for anything that was applied before and is now gone.

let applied = new Set();                      // columns currently applied in the embed

function pushRuntimeFilters(embed, desired) { // desired: [{ columnName, operator, values }]
  const wanted = new Set(desired.map(f => f.columnName));
  const clears = [...applied]
    .filter(col => !wanted.has(col))
    .map(columnName => ({ columnName, operator: RuntimeFilterOp.EQ, values: [] }));

  embed.trigger(HostEvent.UpdateRuntimeFilters, [...desired, ...clears]);
  applied = wanted;
}

// Re-render: runtimeFilters in the config start from scratch, so reset the tracker.
function onRerender() { applied = new Set(); }

Two more rules. Always call embed.destroy() before re-rendering, and reset your tracker when you do. And because the event also resets the object to its original state, any drill the user made is cleared on every push docs.

/** The clicked point, for a left-click and for a context-menu action. */
function clickedPoint(payload) {
  const d = payload?.data ?? payload ?? {};
  const cmp = d.contextMenuPoints;
  return d.clickedPoint
    ?? (Array.isArray(cmp) ? cmp[0] : cmp?.clickedPoint)   // object on tables, array on some surfaces
    ?? d.selectedPoints?.[0]
    ?? null;
}

/** The row's attribute values as [{ column, value }]. Nulls dropped. */
function pointAttributes(point) {
  if (!point) return [];
  const list = v => [].concat(v ?? []);          // docs sample shows a single object, field notes an array
  const attrs = list(point.selectedAttributes).length
    ? list(point.selectedAttributes)
    : list(point.deselectedAttributes);          // table measure-cell click
  return attrs
    .map(a => ({ column: a.column?.name, value: a.value }))
    .filter(a => a.column && a.value != null && a.value !== '' && a.value !== '{Null}');
}

const BUCKET = /^(Day|Week|Month|Quarter|Year)\((.+)\)$/i;

/** "Month(Order Date)" becomes { bucket: 'month', name: 'Order Date' }. */
function splitBucket(column) {
  const m = BUCKET.exec(String(column).trim());
  return m ? { bucket: m[1].toLowerCase(), name: m[2] } : { bucket: '', name: column };
}

/** Epoch seconds (accepts seconds or milliseconds). */
function toEpochSec(v) {
  const n = Number(v);
  return n >= 1e11 ? Math.floor(n / 1000) : n;
}

/** Inclusive last second of a week/month/quarter/year bucket, in UTC. */
function bucketEndSec(bucket, startSec) {
  const d = new Date(startSec * 1000);
  const y = d.getUTCFullYear(), mo = d.getUTCMonth(), da = d.getUTCDate();
  const next = {
    week: Date.UTC(y, mo, da + 7),
    month: Date.UTC(y, mo + 1, 1),
    quarter: Date.UTC(y, mo - (mo % 3) + 3, 1),
    year: Date.UTC(y + 1, 0, 1),
  }[bucket];
  return Math.floor(next / 1000) - 1;
}

/** A clicked attribute becomes a runtime filter the detail Liveboard honors. */
function toRuntimeFilter({ column, value }) {
  const { bucket, name } = splitBucket(column);
  if (!bucket) return { columnName: name, operator: RuntimeFilterOp.IN, values: [String(value)] };
  const start = toEpochSec(value);                       // NUMBER, UTC
  if (bucket === 'day') return { columnName: name, operator: RuntimeFilterOp.IN, values: [start] };
  // Month / quarter / year clicks give the START of the bucket: send the whole range.
  return { columnName: name, operator: RuntimeFilterOp.BW_INC, values: [start, bucketEndSec(bucket, start)] };
}

async function onPointClick(payload) {
  const vizId = payload?.data?.vizId;
  if (DRILL_VIZ && vizId && vizId !== DRILL_VIZ) return;

  const clicked = pointAttributes(clickedPoint(payload)).map(toRuntimeFilter);
  if (!clicked.length) return;                           // nothing to scope by

  // Filters the user already set on the board. Optional: fall back to the click alone.
  const source = embed;
  let boardFilters = [];
  try {
    // The docs disagree on the envelope: the SDK reference types it { liveboardFilters, runtimeFilters },
    // the host events page describes an array. Accept both, and both item keys (`column` was observed).
    const res = await source.trigger(HostEvent.GetFilters);
    const list = Array.isArray(res) ? res : (res?.liveboardFilters ?? []);
    boardFilters = list
      .map(f => ({ columnName: f.column ?? f.columnName, operator: RuntimeFilterOp[f.operator] ?? RuntimeFilterOp.IN, values: f.values }))
      .filter(f => f.columnName && Array.isArray(f.values) && f.values.length);
  } catch { /* click only */ }
  if (embed !== source) return;                          // user navigated while we waited

  // One entry per column. The clicked value wins over a board filter on the same column.
  const byCol = new Map();
  [...boardFilters, ...clicked].forEach(f => byCol.set(f.columnName, f));
  openDetail([...byCol.values()]);
}

/** Fill {Column} placeholders and refuse anything that is not http(s). */
function resolveLink(template, row) {
  const url = template.replace(/\{([^{}]+)\}/g, (_, c) => encodeURIComponent(String(row[c.trim()] ?? '')));
  try { const u = new URL(url); return ['http:', 'https:'].includes(u.protocol) ? u.href : ''; }
  catch { return ''; }
}
const DETAIL_MODEL   = '<record-level-model-guid>';             // one row per record
const DETAIL_COLUMNS = ['Record Id', 'Order Date', 'Customer Name', 'Amount'];
const SCOPE_COLUMNS  = new Set(['Order Date', 'Employee Name', 'Territory', 'Region']);   // allowlist

/** MM/DD/YYYY in UTC: the date literal the search parser accepted on the cluster tested. */
function mdy(sec) {
  const d = new Date(sec * 1000), p = n => String(n).padStart(2, '0');
  return `${p(d.getUTCMonth() + 1)}/${p(d.getUTCDate())}/${d.getUTCFullYear()}`;
}

function buildQuery(scope) {
  const clauses = [];
  for (const { column, value } of Array.isArray(scope) ? scope : []) {
    const { bucket, name } = splitBucket(column);          // same helper as the frontend
    if (!SCOPE_COLUMNS.has(name)) continue;                // the browser cannot choose columns
    const clean = String(value).replace(/['\\]/g, '');   // strip quotes AND backslashes: literals are single-quoted
    if (!bucket) { clauses.push(`[${name}] = '${clean}'`); continue; }
    const start = toEpochSec(value);
    if (bucket === 'day') clauses.push(`[${name}] = '${mdy(start)}'`);
    else clauses.push(`[${name}] >= '${mdy(start)}' [${name}] <= '${mdy(bucketEndSec(bucket, start))}'`);  // verify on your cluster
  }
  return [DETAIL_COLUMNS.map(c => `[${c}]`).join(' '), ...clauses].join(' ');
}

1. Scope

Limit where the action appears: vizIds for one viz, liveboardIds for a board, plus orgIds and groupIds for entitlements. 3. Pick the narrowest position

A context-menu action works from the clicked point, so it exposes less than a viz-level menu action that can pull every row. Choose the position that minimizes the payload. The docs suggest the context menu when you want to send a single row rather than the whole data set docs.

Fetch discipline in your own code

Your page often makes its own REST calls: listing Liveboards, loading filter values, discovering columns. The usual traps are not specific to ThoughtSpot. This is general engineering practice, not a documented rule:

  • Do one fetch and derive from it. For example, load a filter's values once and compute dependent lists locally rather than calling per control.
  • Cache by object id, and share an in-flight request between callers so two components asking for the same thing produce one call.
  • Do not start a REST call per visualization on page load (an N+1 pattern); batch or defer until needed.
  • Keep your bearer token in sync with the embed session so you do not re-authenticate on every call. See Authentication.

Environments and releases

Promote Liveboards, Models and settings from dev to test to prod, and keep your SDK in step with Cloud releases.

An environment is an Org plus a Git branch. You author in dev only, and promote by Git, never by hand-editing prod.

Two limits to know up front

The built-in Git integration (the /vcs/git APIs) supports GitHub and GitHub Enterprise only docs. Deploying to several Orgs in one cluster in parallel is not supported, so loop sequentially and stop on the first failure docs.

Prod must run exactly what test verified. What do you pass to the deploy call?

Deploy uses the branch head unless you pass commit_id, so the head can move after you verified. Parallel Org deploys are not supported.docs

Multi-tenant SaaS: one dev Org, one release branch, then a sequential deploy to each customer Org with a script. Coaching and webhooks are per Org, so repeat them per customer.docs

Regulated: require PR approval on the environment branches, keep VALIDATE_ONLY as a mandatory CI gate, and deploy only tagged commit SHAs so every prod change maps to an approved Git commit.

Go deeper: the mental model, environment layouts and the tools about 3 min

ThoughtSpot defines an environment as a linked pair of an Org and a Git branch. The pair can only export (commit) or import (deploy commits). All development happens in the dev environment. You commit to the dev branch, move the change to the next environment's branch with normal Git tooling, and deploy that branch into the target Org.docs

Two details are easy to miss. First, ThoughtSpot does not recommend committing to Git and then deploying back into the dev environment. Second, objects created by a deploy are new objects in the target: you still set sharing, tags and custom actions on them afterward.docs
